# CI Pipeline — Design

**Goal:** Every pull request runs the essential quality gates — lint/format, typecheck, build, unit tests, and a packaging smoke test — with no dependency on any external service. Slow, network-dependent checks run nightly instead.

**Scope:** Two GitHub Actions workflows, plus the introduction of Biome as the repo's lint/format toolchain (the repo has neither today). Release/publish automation is **out of scope**.

## Decisions

These were settled during brainstorming and are not open questions:

| Decision | Choice | Why |
|---|---|---|
| Lint/format toolchain | **Biome** | One dev dependency, one config, seconds to run. Three of four packages are pure TypeScript libraries. Biome 2.5.8 also ships `react` and `next` rule domains, so `packages/web` loses nothing by not running ESLint. |
| Network tests on PRs | **No** — nightly + `workflow_dispatch` | They hit a live public RPC with 120 s timeouts. A gate that goes red for reasons outside the diff stops being read. |
| Node version | **24 only** | Matches `.mise.toml`, so CI and local dev are one configuration. Accepted risk: a break on node 20–22 (allowed by root `engines`) is not caught. |
| Runner setup | **`jdx/mise-action@v2`** | Reads the existing `.mise.toml`, so node/pnpm versions stay pinned in one file rather than duplicated into workflow YAML. |

## Global constraints

- **Build must run before typecheck.** `miner`, `safe-config` and `web` import `@safe-vanity-blockie/core` through `dist/index.d.ts`, and no tsconfig maps that to `src`. `packages/web/tsconfig.json` additionally includes `.next/types/**/*.ts` and `next-env.d.ts`, both generated by `next build`. `pnpm -r typecheck` on a clean checkout therefore fails unless `pnpm -r build` ran first. This is a property of the repo, not something CI should work around.
- **`pnpm install --frozen-lockfile` everywhere.** It fails on a stale lockfile, which is a check in its own right, and it keeps the `minimumReleaseAge` supply-chain guard in `pnpm-workspace.yaml` meaningful.
- **Least privilege:** every workflow declares `permissions: contents: read`. Neither workflow needs a token beyond checkout.
- **No secrets required.** Network tests default to a public RPC; `TEST_RPC_URL` stays an optional repository variable.
- **Commit style:** conventional commits.

## File structure

| File | Responsibility |
|---|---|
| `.github/workflows/ci.yml` | PR + `main` gate: `lint` and `build-test` jobs |
| `.github/workflows/nightly.yml` | Scheduled + manual network tests |
| `biome.json` | Formatter and linter configuration, tuned to the existing code style |
| `.git-blame-ignore-revs` | Excludes the mechanical format commit from `git blame` |
| `package.json` (root) | Adds `@biomejs/biome` dev dependency and `lint` / `format` scripts |
| `packages/core/package.json` | Removes the bogus `test:network` script (see below) |
| `packages/miner/src/cli.ts` | Entry-point guard fix so the CLI runs through a bin symlink |
| `packages/miner/test/bin.test.ts` | Regression test for that guard |

## 1. `ci.yml`

**Triggers:** `pull_request` (all branches) and `push` to `main`.

**Concurrency:** group on `${{ github.workflow }}-${{ github.ref }}`, with `cancel-in-progress` set to `${{ github.event_name == 'pull_request' }}` — superseded PR runs are cancelled, `main` runs always complete.

**Shared setup steps** (both jobs):

1. `actions/checkout@v5`
2. `jdx/mise-action@v2` — installs node 24 and pnpm 11 from `.mise.toml`
3. Resolve the pnpm store path into `$GITHUB_ENV`, then `actions/cache@v4` keyed on `hashFiles('**/pnpm-lock.yaml')` with an OS-scoped restore key
4. `pnpm install --frozen-lockfile`

### Job `lint`

Runs `pnpm biome ci .` — format check, lint, and import-order assist in one pass, no build required. Expected to finish in well under a minute, so it is the fast-fail signal.

### Job `build-test`

Runs, in this order:

1. `pnpm -r build` — topological, so `core` → `safe-config` → `miner`/`web`. `next build` runs here with `NEXT_TELEMETRY_DISABLED=1`.
2. `pnpm -r typecheck`
3. `pnpm -r test` — vitest, offline, 35 test files
4. Packaging smoke test (below)

The two jobs run in parallel and each install independently; the pnpm store cache makes the duplicated install cheap, and it keeps a lint failure legible on its own.

### Packaging smoke test

`safe-vanity-blockie` is published to npm as a CLI, and the failures that matter there — an incomplete `files` array, a missing shebang, a `dist` that does not stand alone — are invisible to vitest. This is the only check in CI with no local equivalent.

`miner` depends on `core` and `safe-config` via `workspace:*`, which `pnpm pack` rewrites to `0.1.0`. Neither package is on the registry, so a naive `npm install <miner.tgz>` cannot resolve them. The step therefore:

1. Packs all three publishable packages into `$RUNNER_TEMP`
2. Writes a throwaway `package.json` there that depends on the miner tarball by `file:` path and pins `@safe-vanity-blockie/core` and `@safe-vanity-blockie/safe-config` to their sibling tarballs via npm `overrides`
3. Runs `npm install`, then executes `node_modules/.bin/safe-vanity-blockie --help` and asserts a zero exit

This was validated during design rather than assumed: the three-tarball install with `overrides` resolves cleanly, installing 31 packages in about six seconds. If it later proves brittle, the fallback is to assert on the packed tarball's contents (`dist/cli.js` present, shebang intact, `bin` target exists) and drop the install, which keeps most of the signal with none of the resolution machinery.

**Validating it found a shipped bug.** Running the packed CLI through the npm-installed bin produced zero bytes of output and exit code 0. `packages/miner/src/cli.ts` guards its entry point with `import.meta.url === pathToFileURL(process.argv[1]).href`; `import.meta.url` is always the real path, but npm installs a bin as a *symlink*, so the comparison fails and `main()` never runs. It does not reproduce locally because pnpm writes a shell shim instead, which passes the real path. This means `npx safe-vanity-blockie` — the entry point the README and the web app's CLI handoff both document — currently does nothing.

The fix (resolving `process.argv[1]` through `realpathSync` before comparing) and a regression test that invokes the built CLI through a symlink are part of this work, and must land before the smoke test step, which would otherwise fail. The smoke test asserts on non-empty output specifically because this failure mode exits 0.

## 2. `nightly.yml`

**Triggers:** `schedule` at `0 4 * * *`, plus `workflow_dispatch` for on-demand runs.

Same setup steps, then `pnpm -r build` followed by `pnpm -r test:network`. Node 24.

`packages/core`'s `test:network` script is `vitest run --mode network`, which re-runs the ordinary unit suite under a different mode name — `core` contains no `.network.test.ts` files at all. It is deleted as part of this work so a green nightly means the network suites actually ran. `web` has no `test:network` script and is skipped by `pnpm -r`, which is correct.

No notification wiring. Scheduled-run failures surface in the Actions tab and through GitHub's default notifications; anything richer is a separate decision.

## 3. Biome adoption

Pinned to `@biomejs/biome@2.5.8`. Every value below was validated by running that version against the repo during design; the measured results are recorded under "Measured impact".

**Configuration** (`biome.json`), chosen to match the code already in the repo rather than to impose a new style:

- `formatter`: space indent, width 2, `lineWidth: 100` — measured, not guessed. At 100 the format pass rewrites 23 `.ts`/`.tsx` files; at 110 it rewrites 38, because it re-joins lines the author had wrapped by hand. The repo was evidently written to roughly a 100-column budget.
- `javascript.formatter`: `quoteStyle: "single"`, `semicolons: "asNeeded"` — already the house style
- `json.formatter.enabled: false`. Biome's JSON formatter expands the deliberately compact one-line `exports` and `files` entries in the package manifests. JSON still gets parsed and linted; only reformatting is off.
- `linter`: recommended rules, with `style/useTemplate` disabled (see below), and the `react` **and `next`** domains enabled through an `overrides` entry scoped to `packages/web`. Biome 2.5.8 does ship Next.js framework rules — correcting an assumption made earlier in brainstorming, where Biome was chosen partly on the belief that it had none.
- `vcs`: git-aware, reusing `.gitignore`
- `files.includes`: `["**", "!**/dist", "!**/.next", "!**/node_modules"]`. No trailing `/**` — since Biome 2.2 that form is wrong and trips `suspicious/useBiomeIgnoreFolder`.

**`style/useTemplate` is disabled.** It fires 64 times, essentially all of them on the `'0x' + '11'.repeat(20)` idiom used to build fixture addresses in tests. Concatenation is clearer than interpolation for that, the rule is informational so it would never fail CI, and 65 standing diagnostics on every local run trains people to ignore the output.

**Root scripts:** `lint` (`biome check .`) and `format` (`biome check --write .`).

**Measured impact.** `biome check --write` (format plus safe fixes plus import sorting) touches 44 files, +300/−187 lines. What survives and needs human judgement:

| Rule | Count | Location |
|---|---|---|
| `correctness/useExhaustiveDependencies` | 3 errors | `packages/web/components/MiningView.tsx:56` — missing `minContrast`, `state.nextStart`, `twoColor` |
| `security/noDangerouslySetInnerHtml` | 1 error | `packages/web/components/Blockie.tsx:15` |
| `suspicious/noImplicitAnyLet` | 1 error | `packages/miner/src/cli.ts:235` |
| `correctness/noUnusedImports` | 2 warnings | `packages/miner/src/cli.ts:18`, `packages/miner/src/report.ts:4` |
| `suspicious/noConfusingVoidType` | 1 warning | `packages/core/src/miner.ts:73` |
| `complexity/useOptionalChain` | 1 warning | `packages/web/test/MiningView.integration.test.tsx:64` |

`biome ci` exits 1 on the errors; the warnings alone would not fail it.

The three `useExhaustiveDependencies` errors are the only ones that could hide a real bug or a deliberate choice — that effect drives the worker pool, and adding a dependency there could restart mining. They get investigated, not auto-fixed. `noDangerouslySetInnerHtml` is deliberate: `Blockie` renders SVG markup produced locally by the pure `blo` port, never anything user-supplied. It gets a narrow inline suppression carrying that reason, not a disabled rule.

**Landing order — three commits, deliberately separated:**

1. `chore: add biome config and scripts` — configuration only, no source changes
2. `style: format repo with biome` — mechanical, no behavioural change; its SHA is added to `.git-blame-ignore-revs`
3. `fix: resolve biome lint findings` — real fixes for whatever the recommended rule set flags

Rule findings are fixed, not blanket-disabled. Any rule genuinely worth turning off is raised for a decision with its rationale, and disabled narrowly in `biome.json` rather than with inline suppressions.

**Known cost:** commit 2 touches nearly every source file and will conflict with any work in flight. This was accepted when the lint gate was chosen.

## 4. Branch protection

Not automatable from the repo. Once both workflows are on `main`, `lint` and `build-test` are marked as required status checks for `main`; nightly stays unrequired. This is a manual step in repository settings and is called out in the implementation plan as such.

## Verification

The design is satisfied when:

- A PR shows exactly two required checks, both green on the current `main` content
- Deliberately breaking a type, a test, or formatting turns the corresponding job red, and only that job
- `pnpm -r typecheck` succeeds in CI (it does not on a clean checkout without a prior build — the ordering constraint is real, and a green typecheck step proves it is respected)
- `nightly.yml` can be triggered manually and runs the two network suites
- `safe-vanity-blockie --help` prints usage text from an npm-installed package, not silence
- No workflow reads a secret

## Out of scope

Release/publish automation, changesets or version bumping, Dependabot and `pnpm audit`, coverage reporting and thresholds, preview deployments for `packages/web`, `.next/cache` reuse across runs, and multi-OS or multi-node matrices.
